# Unity 2D 플랫포머 물 표면 렌더링 4가지 구현 비교

슬라임 점프 게임(URP, 2.5D)에 가장 적합한 물 표면 렌더링은 **하이브리드 방식(D)**이다. CPU 스프링 시뮬레이션으로 자연스러운 파동 물리를 확보하고, 1D 높이 텍스처를 통해 Shader Graph에 전달하면 시뮬레이션 해상도와 시각적 해상도를 분리할 수 있다. 스프링 체인(A) 단독도 충분히 실용적이며 구현 난이도가 가장 낮고, 순수 Shader(B)는 동적 반응이 약하다. 4가지 방식의 구현 패턴, 퍼포먼스, ripple 반응성을 아래에서 비교한다.

---

## A. 스프링 체인 — 가장 검증된 2D 수면 시뮬레이션

수면을 **N개 수직 스프링 포인트**로 분할하고, 각 포인트에 후크 법칙(Hooke's Law)의 복원력과 감쇠를 적용한 뒤 인접 포인트 간 속도를 전파하는 방식이다. Envato Tuts+의 Alex Rose 튜토리얼(Unity 구현)과 prime31 블로그가 사실상 표준 레퍼런스이며, 인디 2D 플랫포머에서 가장 널리 사용된다.

**핵심 물리 루프**는 3단계로 구성된다. 첫째, 각 포인트에 `force = -springConstant × displacement - damping × velocity`를 적용해 개별 진동을 계산한다. 둘째, 인접 포인트 간 높이 차이에 `spread` 계수를 곱해 속도를 전파한다. 이 전파 패스를 **프레임당 8회 반복**하면 파동이 한 프레임 내에서 여러 포인트를 건너뛸 수 있어 자연스러운 전파 속도를 얻는다. 셋째, 위치를 갱신한다. 전형적 상수는 `springConstant=0.02`, `damping=0.04~0.1`, `spread=0.05~0.1`이다.

**슬라임 진입 시 ripple**은 `OnTriggerEnter2D`에서 슬라임의 `Rigidbody2D.velocity.y`를 스케일링해 해당 x좌표의 스프링 포인트에 속도 임펄스를 가한다. prime31은 슬라임의 `Bounds` 폭만큼 여러 스프링에 힘을 분산하는 방식을 제안하는데, 단일 포인트 임펄스보다 더 자연스러운 V형 파동을 만든다.

**렌더링**은 두 가지 패턴이 있다. LineRenderer + 세그먼트별 Mesh 방식(Tuts+ 원본)은 **~N개 드로우콜**이 발생해 200+ 포인트에서 성능 문제를 일으킨다. **단일 동적 Mesh 방식**(Ilham Effendi 최적화)이 권장된다. 상단 행(스프링 위치) + 하단 행(고정 바닥) 총 `N×2` 버텍스로 트라이앵글 스트립을 구성하면 **1 드로우콜**로 전체 수체를 렌더링한다. 하단 버텍스에 어두운 vertex color를 지정하면 깊이 그라데이션도 자동으로 얻는다.

| 항목 | 값 |
|------|-----|
| 권장 포인트 밀도 | 월드 유닛당 **5~10개** |
| 10유닛 수체 기준 | 50~100 스프링 |
| CPU 비용 | O(N), 100포인트 기준 **<0.1ms** |
| 드로우콜 (단일 Mesh) | **1** |
| 파동 방향 | 좌우 전파 (2D 사이드뷰에 적합) |

**한계**: 매 프레임 `mesh.vertices` 배열을 CPU→GPU로 업로드해야 한다. 100~200 버텍스 수준에서는 무시할 수 있지만, 시뮬레이션 해상도와 시각적 해상도가 동일하게 묶인다. 포인트를 늘리면 시각적으로 부드러워지지만 같은 `spread` 값에서 파동 전파가 느려지므로 상수 재조정이 필요하다.

## B. URP Shader Graph vertex displacement는 동적 반응에 한계가 있다

Quad 메쉬에 사인/노이즈 기반 vertex displacement를 적용하면 **앰비언트 파동(항상 움직이는 잔물결)**은 매우 효과적이다. Shader Graph의 Vertex Position 포트에 `sin(worldPos.x × frequency + _Time × speed) × amplitude`를 연결하면 CPU 연산 없이 GPU만으로 물결이 생긴다. Daniel Ilett의 테스트에서 GTX 1070 기준 **1,024개 워터 메쉬를 동시에 렌더링해도 ~400fps**를 유지했을 정도로 GPU 비용이 극히 낮다.

**치명적 제약: URP에서 테셀레이션을 지원하지 않는다.** 단순 Quad(4 버텍스)에는 displacement 효과가 전혀 보이지 않으며, **사전에 세분화된 메쉬**(예: 64×2 스트립)가 반드시 필요하다. Cyanilux, Daniel Ilett, Ameye 모두 이 점을 명시적으로 강조한다.

**슬라임 진입 ripple**을 순수 셰이더로 구현하려면, C#에서 `_RippleCenter`(Vector4: xy=위치, z=시작시간, w=강도)를 4개 정도의 프로퍼티로 전달한 뒤 셰이더에서 `sin(distance × freq - elapsed × speed) × fadeout`을 계산한다. 그러나 이 방식에는 근본적 문제가 있다.

- **배열 미지원**: Shader Graph 블랙보드에 배열 타입이 없다. 다중 ripple 포인트는 Custom Function 노드(HLSL 파일 모드)로 우회해야 한다.
- **파동 물리 부재**: 사인 함수는 감쇠와 전파, 간섭, 반사를 시뮬레이션하지 못한다. 스프링 기반 파동의 자연스러운 물리적 행동(에너지 감소, 경계 반사, 비선형 진폭)을 재현할 수 없다.
- **"인터랙티브" 느낌 부족**: 예측 가능한 수학 함수이므로 플레이어가 반복 진입할 때 기계적으로 느껴질 수 있다.

**이 방식이 적합한 경우**: 동적 반응이 불필요하고 앰비언트 파동만 필요한 배경 물, 또는 하이브리드(D) 방식의 렌더링 레이어로 사용할 때. 단독으로는 슬라임의 빈번한 진입/이탈에 충분한 시각 반응을 제공하기 어렵다.

## C. 스프라이트 애니메이션 — Hollow Knight도 이걸로 충분했다

가장 단순한 방식이며, 놀랍게도 가장 성공적인 인디 게임들이 이 접근법을 사용한다. **Hollow Knight**은 반투명 컬러 스프라이트/쿼드의 레이어링 + 패럴랙스 + 파티클로 물을 표현한다. **Celeste**는 틴팅된 직사각형에 미세한 디스토션만 추가했다. **Cuphead**은 1930년대 애니메이션 스타일의 수작업 프레임 애니메이션을 사용한다. 세 게임 모두 동적 수면 변형 없이도 뛰어난 비주얼을 달성했다.

**구현 패턴**은 크게 세 가지다. 첫째, **애니메이트 스프라이트 시트** — 4~12프레임의 수면 애니메이션을 8~12fps로 재생한다. 둘째, **UV 스크롤** — 셰이더에서 UV 오프셋을 `_Time`으로 이동시켜 흐르는 물 효과를 만든다. SpriteRenderer 기본 셰이더는 UV 스크롤을 지원하지 않으므로 커스텀 셰이더가 필요하다. 셋째, **다중 레이어 패럴랙스** — 서로 다른 Z 깊이/속도로 반투명 수면 레이어를 배치해 깊이감을 연출한다.

**스플래시/ripple은 별도 파티클**로 처리한다. `OnTriggerEnter2D`에서 ParticleSystem 프리팹을 인스턴스화하고, `startSpeed`와 `emissionCount`를 슬라임의 진입 속도에 비례시킨다. 수면 자체는 변형되지 않으므로 파티클이 정적 표면 위에 오버레이되는 시각적 불일치가 발생할 수 있다.

**이 방식이 충분한 조건**: 물이 게임의 핵심 메카닉이 아닌 배경 요소일 때, 스타일라이즈드 아트에서 동적 반응보다 분위기가 중요할 때, 타겟 플랫폼의 성능이 극도로 제한될 때. 그러나 **슬라임이 자주 진입/이탈하는 이 프로젝트의 맥락에서는 수면이 전혀 반응하지 않으면 인터랙션 피드백이 부족**하다고 판단된다.

## D. 하이브리드 — 시뮬레이션 정밀도와 시각 품질의 최적점

CPU 스프링 시뮬레이션(A의 물리)의 결과를 GPU 셰이더(B의 렌더링)에 전달하는 방식이다. 이 아키텍처의 핵심 이점은 **시뮬레이션 해상도와 렌더링 해상도의 분리**다. CPU에서 50개 스프링으로 파동 물리를 계산하고, GPU에서 500+ 버텍스 메쉬에 보간된 높이를 적용하면 적은 연산 비용으로 매끄러운 수면을 얻는다.

**CPU→GPU 데이터 전달에는 세 가지 경로**가 있으며, 각각 트레이드오프가 다르다.

**1D 텍스처 인코딩이 URP Shader Graph에 가장 실용적이다.** N×1 `RFloat` 포맷의 `Texture2D`에 스프링 높이값을 기록하고 `Texture2D.Apply()`로 업로드한 뒤, Shader Graph의 `Sample Texture 2D LOD` 노드로 버텍스 스테이지에서 샘플링한다. 하드웨어 바이리니어 필터링이 스프링 포인트 사이를 **자동으로 부드럽게 보간**해주므로 추가 보간 코드가 불필요하다. 128개 스프링 기준 텍스처 크기는 **512바이트**에 불과하다.

**ComputeBuffer(`StructuredBuffer`)는 성능이 가장 좋지만** Shader Graph에서 네이티브로 지원되지 않는다. Custom Function 노드(파일 모드)에서 외부 `.hlsl` 파일을 참조해 `StructuredBuffer<float> _HeightBuffer`를 선언해야 한다. 데이터 전송량은 100 float × 4바이트 = **400바이트**로 무시할 수준이다.

**`MaterialPropertyBlock.SetFloatArray()`는 URP에서 피해야 한다.** SRP Batcher와 호환되지 않아 워터 바디마다 배칭이 깨진다. 또한 CBUFFER의 float 배열은 float4 정렬 규칙 때문에 원소당 16바이트를 소비한다.

**셰이더 측 추가 효과**가 이 방식의 진정한 강점이다. CPU 스프링 높이로 vertex displacement를 적용한 후, 같은 셰이더 내에서 다음을 레이어링할 수 있다.

- **깊이 기반 색상**: `Scene Depth`와 수면 깊이 차이로 shallow/deep 컬러를 `Lerp`
- **굴절/왜곡**: URP의 `_CameraOpaqueTexture`를 노이즈 기반 UV 오프셋으로 샘플링 (2D Renderer 사용 시 `_CameraSortingLayerTexture`로 대체)
- **수면 하이라이트**: UV.y 기반 마스킹으로 상단 엣지에 밝은 라인 추가
- **스크롤링 노이즈**: 수체 내부에 `Tiling And Offset` + `Time`으로 유기적 텍스처 움직임

## 이 프로젝트에 권장하는 구현 전략

슬라임이 빈번하게 물에 진입/이탈하는 게임 메카닉, 이미 구현된 `BoxCollider2D` 트리거 기반 부력 시스템, Hollow Knight/Celeste 계열의 스타일라이즈드 비주얼이라는 조건을 종합하면, **방식 D(하이브리드)**가 최적이되 실질적인 구현 복잡도는 A와 크게 다르지 않다.

**구체적 아키텍처**: CPU에서 50~100개 스프링 시뮬레이션을 `FixedUpdate`에서 실행한다. 매 프레임 높이 배열을 N×1 `RFloat` 텍스처에 기록하고 `Apply()`한다. 64×2 세분화 스트립 메쉬에 URP Unlit Shader Graph를 적용하고, 버텍스 스테이지에서 `Sample Texture 2D LOD`로 높이를 읽어 Y displacement를 수행한다. 프래그먼트 스테이지에서 깊이 그라데이션과 스크롤링 노이즈를 추가한다. 스플래시 파티클은 `OnTriggerEnter2D`에서 별도의 ParticleSystem으로 보강한다.

만약 구현 속도를 최우선으로 한다면, **방식 A(스프링+단일 Mesh)**만으로도 충분히 좋은 결과를 얻을 수 있다. Ilham Effendi의 단일 Mesh 최적화 패턴을 기반으로 하면 1 드로우콜, <0.1ms CPU, 자연스러운 파동 물리, 즉각적인 부력 시스템 통합이 가능하다. 방식 A로 시작한 뒤 시각적 폴리시 단계에서 셰이더 레이어를 추가해 D로 확장하는 점진적 접근이 리스크가 가장 낮다.

## 결론

4가지 방식은 배타적이지 않다. **A는 D의 부분집합**이며, B의 앰비언트 파동 기법은 D의 셰이더 레이어에 자연스럽게 통합된다. C는 메카닉적으로 중요하지 않은 배경 물 영역에 병행 사용할 수 있다. 핵심 인사이트는 **스프링 시뮬레이션의 CPU 비용이 무시할 수준**(100 포인트에 <0.1ms)이므로 순수 GPU 방식(B)의 동적 반응 한계를 감수할 이유가 없다는 점이다. 텍스처 기반 데이터 전달이 Shader Graph와 자연스럽게 호환되므로, CPU 물리의 강점과 GPU 렌더링의 유연성을 동시에 취하는 하이브리드 접근이 이 프로젝트의 맥락에서 가장 합리적이다.
