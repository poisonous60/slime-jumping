# 플랫폼 게임 물리 엔진 구현 방식 완전 분석

**Unity 2.5D 물리 플랫포머 'SlimeJumping' 개발을 위한 참고 자료로서, 6개 게임의 물리 구현 방식을 소스코드 레벨까지 분석한 결과, 핵심 결론은 다음과 같다.** 모든 뛰어난 물리 플랫포머는 엔진 내장 물리를 그대로 사용하지 않는다. Getting Over It은 Unity PhysX의 조인트 모터를 "간접 제어"에 활용하고, Celeste는 물리 엔진을 완전히 배제한 커스텀 시스템을 쓰며, Super Meat Boy는 Box2D를 충돌 솔버로만 사용한다. 가장 효과적인 접근은 **하이브리드 방식** — Rigidbody의 충돌/중력 시스템을 활용하되 velocity를 직접 제어하는 것이며, 이것이 SlimeJumping에 최적의 아키텍처다.

## Getting Over It: 조인트 모터가 만드는 "무거운 물리"

Bennett Foddy는 Unity 엔진의 PhysX 물리를 사용하되, 핵심 메커닉을 **3체 조인트 체인(three-body joint chain)** 으로 구현했다. Foddy 본인이 Steam 포럼(2019년 1월)에서 직접 밝힌 구조는 다음과 같다:

```
[항아리(Rigidbody)] ←→ Hinge Joint(회전 모터) ←→ [보이지 않는 중간체(Rigidbody)] ←→ Slider Joint(선형 모터) ←→ [해머 헤드(Rigidbody + Collider)]
```

**Hinge Joint**가 마우스 커서 방향으로의 해머 *각도*를 제어하고, **Slider Joint**가 해머의 *신축 거리*를 제어한다. 핵심은 두 조인트 모두 **모터(motor)** 를 사용한다는 점이다. 모터는 목표 위치에 직접 이동하는 것이 아니라 목표를 향해 **힘을 가하는** 방식이므로, 해머가 마우스를 즉시 따라가지 않고 관성과 지연을 동반한다. `motor.targetVelocity`를 현재 각도와 목표 각도의 차이에 비례하게 설정하고, `motor.force`로 최대 모터 힘을 제한함으로써 "무겁지만 반응하는" 조작감이 만들어진다.

플레이어 캐릭터(항아리+사람)는 **완전히 수동적인 Rigidbody**다. velocity를 직접 건드리는 코드가 전혀 없으며, 모든 이동은 해머가 지형과 충돌할 때 조인트 체인을 통해 전달되는 반작용력에서 비롯된다. 중력은 Unity 기본 중력(약 **-9.81 m/s²** 또는 튜닝된 변형값)을 그대로 사용하며, 커서는 **월드 스페이스**에서 작동한다 — 카메라 이동이 플레이어 조준을 방해하지 않도록 하기 위한 설계다.

Foddy의 **GDC 2015 강연 "Designing with Physics"** 에서 밝힌 핵심 원칙은: PhysX 같은 물리 엔진을 커스텀으로 대체하지 말고, **질량 비율 관리**, **조인트 모터 활용**, **타임스텝 안정성 확보**를 통해 엔진을 "구부리라(bend)"는 것이다. SlimeJumping의 파워 런치 메커닉에서 발사 후 비행 중 물리 인터랙션(바운스, 벽 충돌)은 이 접근법이 가장 적합하다.

## Pogostuck: 바운스 벡터와 360° 부스트의 물리학

Pogostuck은 독특하게 **GameStudio A8(ACKNEX 엔진)** 으로 제작되었으며, PhysX를 물리 시뮬레이션에 사용한다. 개발자 Superku(Hendrik Felix Pohl)가 Steam 포럼에서 직접 확인한 사항들이다.

포고스틱 바운스의 핵심은 세 벡터의 조합이다: **(1) 플레이어의 틸트 각도**(A/D 키로 제어), **(2) 접촉 표면의 법선 벡터**, **(3) 진입 운동량**. 점프 버튼(스페이스바)은 바운스력의 상향 성분을 증폭시킨다. 의사코드로 표현하면:

```
bounceDir = normalize(surfaceNormal + stickDirection * tiltInfluence)
bounceForce = baseBounceForce * (jumpPressed ? jumpMultiplier : 1.0)
velocity = bounceDir * bounceForce + inheritedMomentum
```

가장 독창적인 메커닉은 **360° 부스트**다. 이륙 후 착지 전까지 **최소 285°** 회전하면 "부스트 차지"가 활성화되어 다음 바운스력이 배수로 증가한다. Superku는 720° 더블 부스트도 테스트했으나, "매번 720°를 돌아야 최대 높이를 얻는다는 것이 게임플레이를 악화시킨다"는 이유로 폐기했다. 이 설계는 **회전 관성 관리**를 핵심 스킬로 만든다 — 착지 각도 조준, 부스트 충전, 과회전 방지를 동시에 처리해야 한다.

| 비교 항목 | Getting Over It | Pogostuck |
|-----------|----------------|-----------|
| 엔진 | Unity(PhysX) | GameStudio A8(PhysX) |
| 물리 유형 | 엔진 내장 조인트/모터 | 엔진 물리 + 커스텀 바운스 |
| 입력 | 마우스 → 월드 커서 | 키보드 틸트 + 점프 |
| 이동 원인 | 해머-지형 반작용력 | 포고스틱 바운스 + 틸트 |
| 부스트 | 없음(순수 물리) | 360° 회전 부스트(≥285° 임계값) |

## Egging On과 구구피자: 항아리류의 변형된 물리 시스템

두 게임 모두 발사체 게임이 아닌 **항아리류(Foddian) 등반 플랫포머**다.

**Egging On**(Egobounds, 2025)은 Unity 엔진에서 **실제 달걀 형상의 커스텀 물리**를 구현했다. 리드 프로그래머 Krzysztof Woźnicki는 "달걀의 물리적 특성이 컨트롤러에 잘 반영되도록 집중했다"고 밝혔다. 달걀의 **불균일한 무게중심**이 예측 불가능한 흔들림을 만들고, 좁은 끝으로 착지하면 **높은 점프**, 넓은 면으로 착지하면 **낮은 점프**를 생산하는 것이 핵심 정밀 메커닉이다. 피격 시 달걀이 깨지면 **"노른자 모드"** — **소프트바디 물리 시뮬레이션**으로 전환되어 완전히 다른 물리 특성(미끄러짐, 틈새 통과)을 제공한다. Rigidbody를 기반으로 하되 달걀 형상에 맞는 대규모 커스텀 레이어를 올린 하이브리드 구조다.

**구구피자**(AnomalyGuys, 2025)는 비둘기 배달원이 머리 위 피자의 **균형을 유지**하며 등반하는 게임이다. 피자 스택에 물리 기반 밸런스 시뮬레이션이 적용되어 이동과 점프 시 기울어지며, 피자가 떨어지면 진행을 잃는다. 2.5D 하이브리드(3D 배경 + 2D 픽셀 스프라이트) 구조로, Unity로 제작된 것으로 추정된다.

SlimeJumping의 파워 런치 메커닉에 적용할 수 있는 **궤적 예측 구현법**은 다음과 같다:

```csharp
// Space Ape Games의 드래그 보정 궤적 예측 (가장 정확한 수학적 방법)
float timestep = Time.fixedDeltaTime / Physics2D.velocityIterations;
Vector2 gravityAccel = Physics2D.gravity * rb.gravityScale * timestep * timestep;
float drag = 1f - timestep * rb.drag;
Vector2 moveStep = launchVelocity * timestep;

for (int i = 0; i < steps; ++i) {
    moveStep += gravityAccel;
    moveStep *= drag;
    pos += moveStep;
    trajectoryPoints[i] = pos;
}
```

바운스까지 예측하려면 **별도 물리 씬(Physics Scene)** 을 생성하여 시뮬레이션하는 방법이 가장 정확하다:

```csharp
Scene simScene = SceneManager.CreateScene("Sim", 
    new CreateSceneParameters(LocalPhysicsMode.Physics2D));
// 복제 오브젝트를 sim scene에 이동 → physicsSim.Simulate(fixedDeltaTime) 반복
```

## Celeste의 "feel" 엔지니어링: 소스코드 완전 분석

Celeste는 물리 엔진을 **전혀 사용하지 않는** 순수 커스텀 시스템이다. Player.cs는 약 **5,400줄**의 C# 코드이며, 23개 상태를 가진 상태 머신으로 구현되어 있다. 모든 충돌체는 **AABB(축 정렬 바운딩 박스)**, 모든 위치는 **정수 잠금(pixel-perfect)**, X/Y 이동은 **분리 처리**되며 **1픽셀씩** 충돌을 검사한다. Maddy Thorson의 말을 빌리면: "모든 기법은 타이밍/위치 윈도우를 넓히는 것에 집중되어 있어, 게임이 플레이어 편을 든다."

### 코요테 타임 (Coyote Time)

플랫폼을 떠난 후에도 **0.1초(~6프레임)** 동안 점프 가능:

```csharp
private const float JumpGraceTime = 0.1f; // 6프레임 @ 60fps

if (onGround)
    jumpGraceTimer = JumpGraceTime;  // 지면 접촉 시 리셋
else if (jumpGraceTimer > 0)
    jumpGraceTimer -= Engine.DeltaTime;  // 공중에서 카운트다운

// 점프 조건: jumpGraceTimer > 0 (onGround가 아님!)
```

### 점프 버퍼링 (Jump Buffering)

착지 직전 점프 입력을 **4프레임** 동안 저장하여 착지 즉시 실행:

```lua
-- PICO-8 버전 (명시적 구현)
if (input_j) then p.j_buffer = 4
elseif (p.j_buffer > 0) then p.j_buffer -= 1 end

-- 점프 실행: j_buffer > 0 AND grace > 0 → 점프!
```

코요테 타임과 점프 버퍼링의 **윈도우 겹침**이 핵심이다 — 버퍼가 "점프 의도"를, 코요테 타임이 "점프 가능 상태"를 저장하며, 두 윈도우가 겹치는 순간 점프가 발동된다.

### 가변 점프 높이 (Variable Jump Height)

Celeste의 가변 점프는 **velocity 절단이 아닌 velocity 유지** 방식이다:

```csharp
private const float JumpSpeed = -105f;    // 초기 상향 속도
private const float VarJumpTime = 0.2f;   // 12프레임 유지 윈도우

// 점프 시작
Speed.Y = JumpSpeed;
varJumpTimer = VarJumpTime;

// 매 프레임 업데이트
if (varJumpTimer > 0) {
    varJumpTimer -= Engine.DeltaTime;
    if (Input.Jump.Check)
        Speed.Y = Math.Min(Speed.Y, varJumpSpeed);  // 버튼 홀드 → 속도 유지
    else
        varJumpTimer = 0;  // 버튼 릴리스 → 즉시 타이머 종료, 중력 적용
}
```

짧게 탭하면 즉시 중력에 의해 감속되어 **짧은 홉**, 0.2초 풀 홀드하면 상향 속도 -105가 유지되어 **최대 높이** 점프가 된다.

### 정점 부근 반중력과 비대칭 점프 아크

```csharp
private const float Gravity = 900f;           // 기본 중력 (px/s²)
private const float HalfGravThreshold = 40f;  // 반중력 적용 속도 임계값

// |Speed.Y| < 40 AND 점프 버튼 홀드 → 중력 0.5배
float mult = (Math.Abs(Speed.Y) < HalfGravThreshold && Input.Jump.Check) ? 0.5f : 1.0f;
Speed.Y = Calc.Approach(Speed.Y, maxFall, Gravity * mult * Engine.DeltaTime);
```

**상승 중**: varJumpTimer가 일정 속도를 유지하고, 정점 부근에서 반중력이 적용되어 "떠있는 듯한" 정점 → **하강 시**: 풀 중력(900)이 적용되어 빠르게 가속. 결과적으로 **평평한 정점 + 빠른 하강**의 비대칭 아크가 만들어진다.

### 수평 이동과 공중 제어

```csharp
public const float MaxRun = 90f;      // 최대 수평 속도
public const float RunAccel = 1000f;  // 지면 가속도
private const float AirMult = 0.65f;  // 공중 가속도 배율

float mult = onGround ? 1f : AirMult;  // 공중: 65% 가속
Speed.X = Calc.Approach(Speed.X, MaxRun * moveX, RunAccel * mult * Engine.DeltaTime);
// 지면: 1000 px/s² | 공중: 650 px/s²
```

### 벽 슬라이딩과 벽 점프

벽 슬라이딩은 중력 감소가 아니라 **최대 낙하 속도 캡**을 시간에 따라 변화시킨다:

```csharp
// 벽 슬라이딩: 1.2초에 걸쳐 20 → 160으로 점진적 가속
max = MathHelper.Lerp(MaxFall, WallSlideStartMax, wallSlideTimer / WallSlideTime);
// 초기: max = 20 (매우 느린 슬라이드) → 1.2초 후: max = 160 (일반 낙하)
```

벽 점프는 **벽 반대 방향으로 강제 이동(0.16초)** 을 포함한다:

```csharp
Speed.X = 130f * dir;    // 벽 반대 방향 (MaxRun 90 + JumpHBoost 40)
Speed.Y = -105f;         // 상향 (JumpSpeed)
forceMoveXTimer = 0.16f; // ~10프레임 동안 입력 무시, 벽에서 밀려남
```

### 코너 보정 (Corner Correction)

점프 중 천장 모서리에 걸리면 **최대 4픽셀**까지 좌우로 밀어 넘겨준다:

```csharp
for (int i = 1; i <= 4; i++) {
    if (!CollideCheck<Solid>(Position + new Vector2(-i, -1))) {
        Position += new Vector2(-i, -1);  // 왼쪽으로 i픽셀 + 위로 1픽셀 이동
        return;
    }
}
```

## Super Meat Boy: "쓰레기 물리"의 정밀한 설계

Tommy Refenes는 커스텀 C++ 엔진("Tommunism Engine")을 작성하고, **Box2D를 충돌 솔버(solver)로만** 사용했다. Refenes 본인의 말: "게임의 어떤 것도 실제 물리에 정확하지 않다. Meat Boy의 이상한 컨트롤은 모두 게임 레이어에서 처리되며, 엔진 레이어가 아니다." 이동 물리를 2개월간 반복 튜닝하여 만든 이 시스템을 그는 **"garbage physics(쓰레기 물리)"** 라고 불렀다.

핵심 조작 설계의 비대칭성: **방향 키를 놓으면 즉시 정지**(지면), 그러나 **방향 전환 시에는 관성에 의한 슬라이딩**이 발생한다. 이것이 "미끄럽지만 반응하는" 조작감의 비밀이다. RUN 버튼은 지면뿐 아니라 **공중에서도 수평 속도 캡을 즉시 변경**하여, 공중 제어의 깊이를 더한다.

벽 점프는 **3가지 변형**이 존재한다: (1) RUN+벽 점프(넓은 각도, 강한 수평력), (2) 일반 벽 점프(중간 각도), (3) 숏 홉 벽 점프(가파른 각도, 약한 힘). **200ms의 벽 점프 입력 버퍼**가 있지만, 특이하게도 **코요테 타임은 구현하지 않았다** (HandmadeCon 2015에서 확인).

가변 점프 높이는 버튼 릴리스 시 **상향 속도를 절단하거나 반전**하는 방식으로, 정점의 "붕 뜨는" 느낌을 방지한다. 물리는 **60fps 프레임 레이트에 묶여 있어** 144Hz 모니터에서 약 2.4배 속도로 작동하는 알려진 이슈가 있다 — 이것은 정밀 플랫포머에서 결정론적 물리를 보장하기 위한 의도적 트레이드오프다.

```
// Super Meat Boy 이동 의사코드 (재구성)
if (on_ground):
    if (direction_pressed):
        velocity.x = accelerate_toward(target * (RUN ? RUN_SPEED : WALK_SPEED), GROUND_ACCEL)
    else:
        velocity.x = 0  // ← 즉시 정지! 핵심 설계 결정
else:  // 공중
    velocity.x = accelerate_toward(target * (RUN ? RUN_SPEED : WALK_SPEED), AIR_ACCEL)
    // RUN 버튼이 공중에서도 속도 캡을 즉시 변경

if (jump_released AND velocity.y < 0):
    velocity.y *= 0  // 또는 반전 — 정점 부유 방지
    
gravity = (velocity.y < 0) ? GRAVITY_RISING : GRAVITY_FALLING
velocity.y += gravity
```

## 항아리류 장르의 난이도 설계 원칙

Bennett Foddy의 설계 철학에서 추출한 핵심 원칙 세 가지:

**첫째, 컨트롤은 정확해야 한다.** Getting Over It의 해머는 플레이어가 지시한 곳으로 정확히 간다 — 좌절은 컨트롤의 부정확함이 아니라 물리 시스템의 관성과 운동량에서 발생한다. 입력과 결과 사이에 물리 법칙이라는 "정직한 중간 과정"이 있기 때문에, 플레이어는 실패를 자신의 탓으로 받아들인다.

**둘째, 입력은 단순하되 결과는 복잡해야 한다.** Getting Over It은 마우스 위치 하나, Pogostuck은 틸트+점프 둘뿐이다. 그러나 조인트 모터의 지연과 관성, 바운스 벡터의 비선형 조합이 최소 입력에서 최대 깊이를 창출한다. SlimeJumping의 파워 런치도 이 원칙을 따라야 한다 — "각도 + 파워" 두 변수가 중력, 관성, 바운스와 결합하여 복잡한 궤적을 만들도록.

**셋째, 축적된 진행의 가시성이 손실의 무게를 결정한다.** Getting Over It의 연속 세계는 떨어질 때 지나온 모든 구간을 눈으로 보게 만든다. Foddy의 표현: "축적한 무언가를 빼앗긴다는 느낌은, 레벨을 다시 시작하는 것과 감정적으로 다르다."

## SlimeJumping을 위한 Unity 하이브리드 물리 설계 제안

연구 결과를 종합하면, SlimeJumping의 최적 아키텍처는 **Dynamic Rigidbody2D + velocity 직접 제어 + 커스텀 상태 관리**의 하이브리드 방식이다.

### 파워 런치 (차징 + 발사) 구현

```csharp
// Update()에서 입력 처리
if (Input.GetButton("Fire1") && isGrounded) {
    chargeTime += Time.deltaTime;
    float t = Mathf.Clamp01(chargeTime / maxChargeTime);
    currentPower = Mathf.Lerp(minForce, maxForce, chargeCurve.Evaluate(t));
    UpdateTrajectoryPreview(currentPower);  // 궤적 미리보기
}
if (Input.GetButtonUp("Fire1") && isCharging) {
    Vector2 launchDir = CalculateAimDirection();  // 마우스/스틱 기반
    rb.velocity = launchDir * currentPower;        // 직접 velocity 설정
    // AddForce(Impulse)보다 velocity 직접 설정이 예측 가능
}
```

**차지-파워 매핑**은 AnimationCurve를 사용하면 디자이너가 런타임에서 곡선을 조정할 수 있어 가장 유연하다. 선형은 밋밋하고, 이차함수(`t²`)는 극적인 차이를 만들며, 제곱근(`√t`)은 초반에 빠르게 차오르는 느낌을 준다.

### 벽 슬라이딩 + 벽 점프

```csharp
// 벽 슬라이딩: 하향 속도 캡 (Celeste 스타일)
if (isTouchingWall && !isGrounded && rb.velocity.y < 0) {
    rb.velocity = new Vector2(rb.velocity.x, 
        Mathf.Max(rb.velocity.y, -wallSlideSpeed));  // 최대 -2~3 유닛/초
}

// 벽 점프: 반대 방향 강제 + 입력 잠금
void WallJump(int wallDir) {
    rb.velocity = new Vector2(-wallDir * wallJumpForce.x, wallJumpForce.y);
    inputLockTimer = 0.15f;  // 0.15초 간 수평 입력 무시 (재흡착 방지)
}
```

### 운동량 보존 바운스

```csharp
private Vector2 lastVelocity;
void FixedUpdate() { lastVelocity = rb.velocity; }

void OnCollisionEnter2D(Collision2D col) {
    Vector2 reflected = Vector2.Reflect(lastVelocity, col.contacts[0].normal);
    float bounce = 0.75f;  // 에너지 보존 계수
    rb.velocity = reflected * bounce;
    // 최소 바운스 속도 보장 (약한 바운스 방지)
    if (rb.velocity.magnitude < minBounceSpeed)
        rb.velocity = rb.velocity.normalized * minBounceSpeed;
}
```

### 추천 파라미터 범위

Getting Over It/Pogostuck 스타일의 **관성+중력 위주** 조작감을 위한 값:

```
Gravity Scale:    3~5 (높을수록 점프에 대한 커밋먼트 증가)
Mass:             1~3 (높을수록 관성 증가)
Ground Accel:     15~30 units/s² (낮을수록 무거운 느낌)
Air Accel:        3~10 units/s² (지면의 20~30%)
Air Decel:        0~5 units/s² (0이면 공중 운동량 완전 보존)
Fall Multiplier:  2.5~4.0 (높을수록 빠른 하강)
Bounce Coeff:     0.6~0.85
Coyote Time:      0.1~0.15초
Jump Buffer:      0.1~0.15초
Wall Jump Lock:   0.1~0.2초
Max Charge Time:  1.5~3.0초
```

## 결론: 하이브리드 물리의 핵심 통찰

6개 게임 분석에서 도출된 가장 중요한 통찰은, **물리 엔진의 "얼마나"를 사용할지가 조작감의 성격을 결정한다**는 것이다. Getting Over It은 물리 엔진에 거의 모든 것을 맡기되 입력-출력 사이에 조인트 모터라는 "완충 장치"를 두었고, Celeste는 물리 엔진을 완전히 배제하고 모든 수치를 직접 통제하여 "관대한 정밀함"을 달성했다. Super Meat Boy는 물리 엔진을 충돌 해결에만 사용하고 이동은 "반복적 튜닝"으로 만들었다.

SlimeJumping이 목표하는 "관성+중력 위주의 파워 런치 조작감"을 위해서는, **발사 후 비행 구간은 물리 엔진에 맡기고**(중력, 바운스, 충돌 반응), **차징/벽 슬라이딩/공중 제어는 velocity를 직접 제어**하는 것이 최적의 균형점이다. 입력 보조 시스템(코요테 타임, 점프 버퍼링, 코너 보정)은 난이도와 무관하게 반드시 구현해야 할 "보이지 않는 관대함"이며, Celeste가 극도로 어려우면서도 공정하게 느껴지는 핵심 이유다.
