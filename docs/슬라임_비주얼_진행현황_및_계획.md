# 슬라임 비주얼/애니메이션 진행 현황 및 계획

## 목적

그레이박스 단계에서 슬라임의 비주얼 공백을 채우고, 프로덕션 단계로 자연스럽게 확장 가능한 구조 마련.

---

## 접근 방식 결정: 절차적 변형 (Procedural Deformation)

### 선택한 방식

**방사 대칭 스프라이트 + 코드 기반 squash/stretch/관성 제어**

- 본체(body)는 완전 방사 대칭 원형 이미지 한 장
- 얼굴(eyes, mouth)은 본체와 분리된 별도 레이어
- 모든 "말랑함", "눌림", "늘어짐", "출렁거림"은 코드가 매 프레임 localScale/position을 조작해서 생성
- 전통적 프레임 애니메이션(Idle 클립, Walk 클립 등)은 사용하지 않음

### 고려했던 다른 선택지

**1. 풀 소프트바디 (노드-스프링 시뮬레이션)**

- 장점: 모든 각도에 자연스럽게 대응, 진짜 물리적 젤리 느낌
- 단점: 과거에 시도했다가 버그로 포기한 경험 있음, 구현 복잡도 높음, 주변 지형 충돌까지 고려하면 작업량 큼
- 판단: 그레이박스 단계에서 선행 투자하기엔 리스크 큼. Phase 2(프로덕션) 후보로 보류.

**2. 본/메시 디폼 (Spine 스타일)**

- 장점: 전통적 애니메이션과 절차적 제어를 동시에 가능
- 단점: Spine 학습 필요, 메시 리깅 작업량, 슬라임에 오버킬
- 판단: 제외.

**3. 프레임 애니메이션 (스프라이트 시트)**

- 장점: 러닝커브 낮음
- 단점: 모든 각도(바닥/벽/천장/경사) 대응하려면 프레임 수 폭증, 절차적 제어와 섞기 어려움
- 판단: 제외.

### 절차적 변형을 선택한 근거

**1. 기존 아키텍처와 궁합이 좋음**

현재 `SlimeController`는 `CircleCollider2D` 하나 + 수동 velocity 관리 구조. 비주얼 레이어를 별도 자식 GameObject로 두면 물리와 완전히 분리되어 Interpolation 충돌 없음. localScale을 마음대로 변형해도 물리에 영향 없음.

**2. 모든 각도에 한 장으로 대응 가능**

방사 대칭 이미지는 어느 방향으로 회전/변형시켜도 실루엣이 깨지지 않음. `surfaceNormal` 한 벡터로 모든 표면(바닥, 벽, 천장, 경사) 대응.

**3. 레퍼런스 확인**

Dicey Dungeons의 젤리, Downwell의 캐릭터, Hollow Knight의 작은 슬라임류 모두 이 접근으로 말랑한 느낌을 구현함. 소프트바디 없이도 슬라임 정체성 유지 가능함이 입증됨.

**4. Phase 2 전환 비용이 낮음**

나중에 소프트바디로 업그레이드하더라도, "SlimeController로부터 위치/상태/법선을 받아 비주얼을 만드는 레이어"라는 구조는 그대로 유지됨. 변형 로직만 교체하면 됨.

**5. 슬라임 느낌의 핵심 4요소가 모두 코드로 가능**

- 호흡 (Idle breathing): `sin` 기반 미세 scale 진동
- 관성 지연 (Motion lag): SmoothDamp로 본체가 물리 위치를 지연 추종
- 속도 기반 stretch: 속도 벡터 방향으로 늘리고 수직 방향으로 누름 (부피 보존)
- 충격 squash: 착지/충돌 시 법선 방향 순간 squash + 탄성 복원

## 이미지 에셋 설계 원칙

### 본체(body)

- 완전 방사 대칭 원형 (1:1 비율)
- 위아래 구분 없는 셰이딩 (방사형 그라데이션 또는 플랫)
- 방향성 있는 하이라이트 금지 (위에서 내려오는 빛 없음)
- 얼굴 없음
- 균일한 두께의 아웃라인
- 근거: 어떤 각도로 회전시켜도 어색하지 않아야 함. 셰이딩에 방향이 박혀 있으면 벽/천장에서 빛이 반대로 가는 이상한 상태 발생.

### 얼굴(eyes, mouth)

- 본체와 분리된 별도 레이어
- 본체가 stretch/squash 중에도 얼굴은 독립적으로 관리
- 근거:
  - 본체와 함께 찌그러지면 눈/입이 납작해져서 어색함
  - 표정 변화(차징/충격/놀람)를 얼굴 스프라이트 스왑으로 구현 가능
  - 본체는 회전(surfaceNormal 기준), 얼굴은 항상 정립(화면 위 기준)의 분리 처리 가능

### "기본 눌림"은 이미지가 아닌 코드로

평지에서의 "가로로 퍼진 슬라임 모습"을 이미지에 그리지 않는 이유:

- 이미지에 눌림이 있으면 "지금 눌린 게 이미지 때문인가 변형 때문인가?" 수학적으로 분리 불가
- 중립 = 원형으로 정의해야 모든 상태 변형(표면 squash + 속도 stretch + 충격 squash)이 독립적으로 합산 가능
- 공중 = 원형, 표면 접촉 = 법선 방향 squash 라는 원칙이 물리적으로도 일관됨

## 앞으로의 계획

### Phase C-0: 정적 배치 (현재 작업)

목표: 이미지가 씬에 보이기만 하면 성공. 변형 없음.

완료 조건: 플레이 모드에서 슬라임이 움직일 때 이미지가 따라다님. 회전/변형은 없어도 됨.

### Phase C-1: 회전 + 얼굴 추종 ✅ 완료

Body와 Face를 분리 제어. SlimeVisual 자체 transform은 identity 유지.

**Body 회전:**
- Attached/Charging: `Body.up = surfaceNormal` (Slerp 보간). 차징 중에도 몸은 표면 기준.
- Airborne: `lastSurfaceNormal` 유지 (이륙 직전 자세 고정, 물구나무 방지).

**Face 위치 오프셋 (회전 아님):**
- Charging: `AimDirection * ChargingProgress * faceChargingScale` — 진행도에 비례해 aim 방향으로 쏠림
- Attached/Airborne: `Velocity * faceOffsetScale` — 이동 방향으로 쏠림
- 방향 잔상: 정지 시 즉시 중앙 복귀가 아닌 마지막 방향에서 `faceLingerDecay` 속도로 서서히 감쇠
- 아이들 드리프트: 리사주 곡선(sin 기반, x/y 주파수 다름) 미세 진동으로 정지 시에도 생명감 유지
- `SmoothDamp`로 부드럽게 보간, `ClampMagnitude`로 최대 거리 제한
- `face.localRotation = identity` (항상 정립)

**깜빡임:**
- `eyes_closed.png` 스프라이트 스왑. 랜덤 간격(3~7초)마다 0.1초간 눈 감음.
- "살아있음" 신호 — 뇌가 깜빡임을 의식 있음으로 해석.

파일: `Assets/Scripts/Visual/SlimeVisual.cs`
에셋: `Assets/Art/Slime/eyes_closed.png`
설정: `SlimeSettings` — `visualSlerpSpeed`, `faceOffsetScale`, `faceOffsetMax`, `faceSmoothTime`, `faceChargingScale`, `faceLingerThreshold`, `faceLingerDecay`, `faceDriftAmplitude`, `faceDriftFreqX`, `faceDriftFreqY`, `blinkDuration`, `blinkIntervalMin`, `blinkIntervalMax`
추가된 API: `SlimeController.AimDirection`, `SlimeController.ChargingProgress`

### Phase C-2: 충격 squash (가장 중요)

슬라임 느낌의 결정적 순간. 구현 우선순위 최상.

구현 요소:

- `SlimeController`의 상태 전환 이벤트 훅 (또는 비주얼 레이어에서 surfaceNormal 급변 감지)
- Airborne→Attached 전환 시 impact 속도에 비례한 squash 강도 계산
- `surfaceNormal` 방향 수축, 접선 방향 팽창 (부피 보존)
- 탄성 복원 곡선 (OutElastic 또는 감쇠 진동)
- 지속 시간 ~0.2~0.3초

검증: 높이에서 떨어져 바닥에 "쿵" 부딪히는 게 시각적으로 느껴지는지.

### Phase C-3: 관성 지연 (Motion lag)

본체 비주얼이 물리 위치를 약간 지연해서 따라감. "점성" 표현의 핵심.

구현 요소:

- `SlimeVisual`의 position을 부모(Slime) 위치로 SmoothDamp 추종
- smoothTime 0.05~0.1초 정도
- 또는 Face만 지연시키고 Body는 즉시 따라가게 할 수도 있음 (튜닝 문제)

검증: 급정거 시 비주얼이 살짝 앞으로 쏠렸다 복원되는지.

### Phase C-4: 속도 기반 stretch

이동/낙하 중 속도 방향으로 늘어나고 수직 방향으로 눌림.

구현 요소:

- `rb.linearVelocity`의 크기와 방향으로부터 targetScale 계산
- 속도 벡터 방향 stretch, 수직 방향 squash (부피 보존: x * y = 1)
- 최대/최소 클램프 (너무 극단적으로 늘어나지 않도록)
- SmoothDamp로 반영

검증: 공중에서 빠르게 이동할 때 진행 방향으로 늘어지는지.

### Phase C-5: 표면 기본 squash

표면 접촉 시 중력에 눌린 기본 형태 유지. 평지에서 "가로로 퍼진 슬라임" 느낌.

구현 요소:

- Attached 상태에서 `surfaceNormal` 방향으로 기본 squash 적용
- 예: `(1.15, 0.85)` 정도, 월드 기준이 아니라 접선/법선 기준
- Airborne 상태에선 `(1, 1)`로 복원
- 상태 전환 시 SmoothDamp로 부드럽게 보간
- 모든 다른 변형(충격, 속도, 호흡)과 합산되어야 함

검증: 벽에 붙으면 벽 수직으로 눌리고, 바닥에 붙으면 수평으로 퍼지는지.

### Phase C-6: 호흡 (Idle breathing)

마지막 디테일. 가만히 있을 때도 "살아있음" 표현.

구현 요소:

- `sin(Time.time * 주기) * 0.02~0.03` 정도의 미세 scale 진동
- 모든 상태에서 항상 활성 (변형들과 합산)
- 주기는 약 2~3초에 한 번

검증: 정지 상태 슬라임이 미묘하게 숨 쉬는 느낌이 나는지.

### Phase C-7: 얼굴 표정 (선택적)

여유가 되면 추가. 없어도 그레이박스엔 충분.

구현 요소:

- eyes/mouth 이미지를 상태별로 여러 장 준비 (기본, 차징, 충격, 졸림 등)
- 상태 이벤트에 따라 SpriteRenderer.sprite 스왑
- 또는 개별 이미지 없이 Face GameObject의 offset/rotation만 미세 조정해도 효과 있음

## 변형 합성 공식 (구현 시 참고)

여러 변형이 동시에 작용하므로 합산 방식을 명확히 해야 함.

```
finalScale = baseSurfaceSquash      (Phase C-5, 표면에 따른 기본 눌림)
           + velocityStretch          (Phase C-4, 속도 기반)
           + impactSquashOverlay      (Phase C-2, 충격 이벤트, 시간 감쇠)
           + breathingOffset          (Phase C-6, sin 기반 미세 진동)

currentScale = Vector2.SmoothDamp(currentScale, finalScale, ref scaleVel, smoothTime)
SlimeVisual.localScale = currentScale
```

- 각 항은 "중립 대비 오프셋"으로 표현 (0 = 변화 없음)
- 최종 적용 시 `(1, 1) + sum(offsets)` 형태
- SmoothDamp로 부드럽게 따라감 → 상태 전환 시 "1프레임 순간이동" 방지
- `smoothTime`은 0.08~0.15초 범위에서 튜닝

## 상태 전환 시 자연스러움 확보

### 우려 사항

벽 슬라이딩 → 바닥 착지 같은 급격한 `surfaceNormal` 변화 시 비주얼이 1프레임에 홱 바뀌면 어색함.

### 대응

1. **SmoothDamp 기반 보간**: `targetScale`이 순간적으로 바뀌어도 `currentScale`은 6~9프레임에 걸쳐 부드럽게 따라감. 이것만으로 대부분 해결됨.

2. **Impact overlay로 중간 단계 덮기**: 표면 전환 시 `normalChange` 각도를 감지해서 impact squash 트리거. 중간에 "어색한 원형 상태"가 나타나지 않고 대신 "강하게 눌린" 상태로 이어져서 일관된 변형으로 인식됨.

3. **비주얼 레이어에서 normal 변화 감지**: `SlimeController` 수정 없이 비주얼 쪽에서만 `Vector2.Angle(prevNormal, currentNormal)`을 재서 threshold 초과 시 impact 트리거. 물리/비주얼 분리 원칙 유지.

## Phase 2 (프로덕션) 장기 계획 — 참고용

현재 Phase C로 충분하다 판단되면 건너뛰어도 됨.

- 본체를 실제 소프트바디(노드-스프링 또는 본 기반 메시 디폼)로 교체
- 주변 지형 인식 (모서리에 휘감기, 좁은 틈에 끼는 등)
- 얼굴 레이어는 Phase C에서 만든 구조 그대로 재사용
- `SlimeVisual` 인터페이스(위치/상태/법선 입력)는 동일 유지 → 하부 구현만 교체
